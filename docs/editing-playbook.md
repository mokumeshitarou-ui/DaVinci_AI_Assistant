# 編集を最初から最後まで進める手順

## まず次の一手を決める

| 現在の状態 | 次にすること |
|---|---|
| 案件・素材だけ分かる | 既存PJ・完成品・作業TLを照合し、既存解析と最初の使える工程を読む |
| 使えるカット計画がある | 現在の実TLと比較し、未配置の1ブロックを配置・保存する |
| カットだけ入っている | 原音と字幕をつなぎ、読戻し後に次のブロックへ進む |
| 顔の指定が無い | 見える客の顔を仮ぼかしし、HTMLから後で追加・解除できる状態へ進む |
| 案件の承認画像が無い | 代表料理カットの仮基準と補正案を作り、前後比較・可逆な適用・保存を進める |
| 機械検査が通った | 実映像・音を確認し、確認した範囲の品質を判定する |
| 書き出しが未依頼 | 編集・保存・利用可能な画像／ビューアによる検収まで進め、動画出力未検証とする |

## 1. 対象と再開地点を確認する

短い案件メモに、素材ルート、対象PJ/TL名とID、依頼範囲、最新のNG、現在の権限、既存成果、次の変更を揃える。同じ催促は同じ1件の割当として扱う。

現在PJを読み、別PJへ移る必要があれば担当自身が保存する。`SaveProject()==true`、対象PJの一致、保存結果を確かめてから切り替える。ユーザー操作中の切替禁止が有効なら切り替えない。未保存を捨てない。

既存の割当PJ・作業TLを使う。完成品・素材確認TLを上書きせず、存在しない場合だけ新規作成する。新規PJ名はSSD案件フォルダー名。通常の新規本編は59.94fpsを標準とし、案件の指定や既存TLのfpsは勝手に変更しない。

計画と実TLのソースパス、ソースin/out、配置in/out、クリップIDを照合する。既存の一致部分を保持し、欠けている部分から再開する。件数が合うだけでは一致としない。

## 2. 素材を観察し、準備できた工程から実配置する

素材一覧、解析へ投入済み、画像生成済み、実際に内容確認済みを区別する。既存台帳・解析・確認結果を使い、同じ入力を繰り返し解析しない。

全素材の概観を一度行い、工程・食材・状態変化・見せ場とソース時刻を拾う。長尺や複数工程は区間ごとに確認し、未確認帯を残す。コンタクトシートは索引であり、未閲覧の素材を一括除外する根拠にはしない。

全素材の精密解析が終わるまで実配置を待たせない。確認できた工程から次の1ブロックを回す。

1. 実映像と原音を見てカット範囲を決める。
2. 素材パス・fps・ソースin/out・配置in/out・イベント・字幕・採否根拠を既存計画へ記録する。
3. 復元可能な作業TLへカットと原音を配置する。
4. 映像と合う字幕を付ける。
5. 保存し、実TLを読戻して計画と比較する。
6. 変更区間と隣接するつなぎを検収し、次の未処理工程へ進む。

通常カットは2～4秒を目安とするが、動作の成立・結果・現場音・字幕を読む時間を優先する。素材1本につき最大2区間などの上限を設けない。同じ動作の反復は詰め、別食材・別工程・状態変化は残す。同じ字幕だからという理由だけで別の動作を削らない。

仕込み→開店→注文調理→提供・実食→締めを実素材に合わせて組む。営業中の追加仕込みや閉店後の準備も対象。見えていない料理名は要確認のまま、確認できる動作を記録する。


### 取材全体の出来事一覧（2026-10-08 ユーザー指定）

本編編集では、取材開始から閉店・片付けまでの小さな出来事を、採用カットから独立した時系列HTMLへ記録する。準備・拭き掃除・洗い物・補充・休憩・まかない等も実映像に基づいて残す。[時系列イベントの共通手順](event-chronology.md)を使い、撮影時計・素材内秒・根拠画像・元映像と未確認区間を接続する。粗い静止画索引を全イベント確認済みにせず、確認できた内容から同じHTMLへ追加する。

## 3. 客席・字幕・原音を本編へつなぐ

### 客席

最新の取材スレッド、NG原文・写真・訂正を案件側で確認し、服装・席・時刻・前後動作から照合する。使用不可と顔ぼかし可を区別する。未確認なら採用確定だけを保留し、候補作成・仮ぼかし・他の工程を続ける。

料理・箸・口元が分かるカメラを選び、提供→食べる動作を、対応する料理の完成カットにつなぐ。時刻の近さだけで料理名を確定しない。本編3～5人、保留2～3人は候補選定の目安で、人数だけを完成条件にしない。

実際に有効な客席カットの人数・秒数・本編タイムコード・営業区間内の分散を確認する。非表示トラックや候補TLを本編採用に数えない。映像の弱い候補で水増ししない。

素材に成立する場合は無人客席・清掃・卓上や器の準備・開店前外観などを橋渡し候補にする。固定尺や固定位置の必須ブロックにはしない。

### 字幕

**目標は1映像カットに1字幕以上（2026-10-08 ユーザー最終指定）。** 必要なら1カットに複数字幕を付ける。どうしても適切な字幕を考えられないカットに限り省略を許容し、字幕対応率85％以上を下限にする。100カットなら85カット以上が最低条件。85％を最初から目標にせず、省略理由をカットごとに残す。料理名の分かる場面だけで終わらず、仕込み・調理・清掃・提供・客席・外観・締めも実映像の事実に合う説明を検討する。

実TLの映像カットIDと字幕ID・本文・表示範囲を照合し、字幕対応カット数M／全映像カット数Nで判定する。必要数はceil(0.85×N)。総字幕数が多くても一部カットへの集中や前カットからのはみ出しで未字幕を埋めた扱いにしない。省略理由・未処理・未確認を区別する。詳細は[カットごとの字幕と品質検収](caption-coverage.md)。

- 実況は短い名詞句・具体的動作。原則1行17字以内、句読点なし、区切りは半角スペース、数字は全角。正式料理名・住所等の必要な複数行は例外。
- 標準開始はカット頭から15フレーム後。通常2～7秒、1秒4字を目安に動作と可読性を優先する。
- 味・気持ち・価格・サイズを推測しない。料理名と価格は案件の確認済み情報に合わせる。
- 隣接する同文は実際の動作に応じて具体化する。省略は前記の理由付き例外として記録する。表示中の動作ずれ、境界に短く残る字幕、顔・料理へのかぶりを直す。
- 案件の既存トラック様式を保持する。字幕データだけでなく実TL・ビューアで表示を確認する。

### 原音

現場音を使い、依頼のないBGM・効果音・ナレーションを足さない。映像と音のソース範囲、同期、チャンネル対応、不要な重複を確認する。

カメラ切替の音量差は3dB以内、つなぎは2～4フレーム、通しは-16LUFS前後、突発音は-3dBTP以下を既存標準の目安にし、実測と聴取で調整する。ゲイン値や音声クリップ数だけで品質合格にしない。無音・音割れ・音ずれ・不自然な環境音の切替を確認する。

## 4. 顔ぼかしを先に作り、HTMLで追加・解除できるようにする

個別指定を初動条件にしない。客席の見える客の顔を暫定対象にし、明示された対象外・ぼかし不要の指定を尊重する。店員等への扱いを無条件に広げず、不明な区分は仮設定として一覧へ出す。

人物・区間ごとの独立したマスク／ノードで実装し、元映像を保持する。人物の追加・解除・範囲修正ができるようにし、焼き込み映像だけを残さない。

承認例のFusion `Blur.XBlurSize=4.5`、`Blend=1` は出発点。依頼のたびに2倍にせず、画面内の顔の大きさ、解像度、合成設定と見た目で調整する。承認映像との比較は案件側で行い、他PCへ設定を配っただけでは再現検証済みにしない。

毎出力フレームに対応する追尾データを用意し、出入り、振り向き、急な動き、遮蔽、鏡、人物IDの切替を点検する。ソースfps・TLfps・速度変更・Fusion時間原点を照合する。横顔・一部見える顔を覆い、顔が消えた後に料理・空席へマスクを残さない。

既存の統合HTMLへ次を接続する。

| 一覧の項目 | 動作・保存 |
|---|---|
| 案件内人物ID、画像／前後付き映像、ソースとTL時刻 | 人物と区間を見て判断できる |
| ぼかし有効／無効、仮設定／指定済み、対象区間 | 追加・解除・区間修正を保存し再読込で復元 |
| 保存した選択とResolveでの実適用状態 | 既存適用経路で反映し、読戻し・PJ保存後に反映済み表示 |
| 顔ゼロ、未解析、検出候補、要追尾修正 | 未解析を顔ゼロ・処理済みと混同しない |

ユーザーが解除した人物を再解析で勝手に復活させない。処理の再実行では人物ID・区間・設定版を照合し、欠けた差分だけ反映する。

「使用不可／カット指定」はぼかしで解除できない。顔ぼかし一覧は採否・NG照合と接続する。対象数・追尾データ・ノード接続・ビューアの効果を確認して保存し、動画出力が未依頼なら最終出力の全フレーム検査は未検証として残す。

## 5. 明るさと料理の色を整える

明るさ標準は存在する。料理を明るく見せ、白い皿・食材・肌の階調と連続カットの自然さを保つ。固定ゲインや特定のクリップ番号を全案件へ適用する方式ではない。

1. 承認画像・ユーザー手動グレードがあれば再利用する。無ければ代表料理カットを選び、白飛び・極端な色かぶりを避けた仮基準と補正案を作る。前後比較をHTMLへ出し、承認済みと仮基準を区別する。
2. 色管理・出力色空間・レンジを確認する。元のグレードを保持し、別ノード／バージョン等で可逆に補正する。基準クリップを勝手に変更せず、補正を二重適用しない。
3. 各クリップの3%、50%、97%と照明変化点で、実際のグレード込み画像を安定取得する。画像内容・時刻・クリップIDを照合する。固定の待機時間だけを正しさの証拠にしない。
4. SDR表示RGBでは `Y'=0.2126R'+0.7152G'+0.0722B'` を明るさ指標とし、食材領域の中央値、RGB上位百分位、上限付近の面積を測る。字幕・黒帯・手・皿を食材の代用にしない。物理輝度ではなく、HDR/Logへ閾値をそのまま流用しない。
5. クリップ別に中間調と明部を整え、白皿の質感、食材の色、肌、隣接カットのつながりを目視する。縮小8bit画像は候補選定用。微小な白飛びは原寸・可能なら高ビット深度で確認する。
6. 設定と対象を読戻し、前後比較・補正範囲を残して保存する。仮基準なら後から差分再調整できる状態にする。

固定中央値0.60、固定ゲイン、他案件の「382番」は探索の実例で、全案件の必須値ではない。既存の白飛びは補正で復元できない。

承認基準への最終一致が未確定でも、仮補正・比較・可逆な適用・保存まで進める。無関係なカット・字幕作業も継続する。仮基準への補正済みを承認済みの品質合格に置き換えない。

## 6. GPT-6.1でも品質判定を省かない分担

Solへは「対象範囲／使える証拠／望む変更／保存するPJ・TL／具体的な確認方法」を一度に渡す。確認済みの実装を案件データへ当てはめ、例外だけを判断する。監督は見ていない素材を合格にせず、修正箇所・時刻・望む状態・根拠を返す。

| 工程 | 合格に必要な確認 | 合格の代わりにしないもの |
|---|---|---|
| 素材・構成 | 内容確認と採否根拠、未確認帯、工程の欠落、実際の本編接続 | ファイル一覧・画像生成・採用率だけ |
| カット・同期 | 実TLのソース／配置範囲、つなぎの映像・音、意図しない隙間や重複 | API成功・計画JSONだけ |
| 字幕 | 1カット1字幕以上を目標、理由付き例外でも対応率85％以上、未処理0件、実際の動作・事実・可読時間・境界・表示 | 総件数の比較だけ・料理名字幕だけ・85％で自動打切り・文書やSRTの存在だけ |
| 色 | 同条件の前後画像、食材領域の測定、階調・色・連続性 | 設定値・自己採点だけ |
| 顔 | 対象全区間の追尾、出入り・遮蔽・輪郭・濃さ、料理への不要な侵入 | 検出数・マーカー・数枚の静止画だけ |
| 原音 | 実聴取、同期・切替・無音・クリップ、必要な測定 | 波形の存在・ゲイン値だけ |
| HTML | 選択の保存復元、操作、差分反映と実TL読戻しの接続 | ファイルの存在や表示だけ |

通常編集は実用完成に達したら次へ進む。色・顔で具体的な不具合がある場合は該当範囲を直す。合格済みで入力が変わっていない検査を繰り返さない。

確認できない映像・音は未確認とし、実証済みの経路で不足区間だけ確認する。無効な入力の同じ試行を繰り返さない。品質の同等性をモデル名だけで保証しない。

## 7. 保存、検収、許可後の出力

編集反映、品質検収、最終動画の検証を分けて報告する。最低限の既存記録へPJ/TL ID、変更範囲、件数、保存結果、実読戻し、確認した映像・音と未検証をつなぐ。ひな形は[こちら](../templates/round-result.md)。新しい台帳を義務として増やすものではない。

レンダー・Quick Export・試し出力・ジョブ投入は明示依頼後。許可されたら重要な変更区間で必要なQAをまとめ、修正後に全編を最少回数で出力する。既存ジョブを重複投入しない。

出力では尺・fps・字幕・音・黒コマ・境界・NG・色と顔を実ファイルで確認する。顔対象区間は全フレーム処理と疑わしい前後の目視を組み合わせ、自動検査と目視範囲を区別する。出力していないものを出力検証済みにしない。

## 8. 例外からの再開

- API応答不明：現在PJ/TLを読戻してから再試行。配置結果不明のまま同じ追加を繰り返さない。
- 操作権の競合：監督が実担当と順番を整理する。ワーカーに新しい待機条件を作らせず、独立した作業を進める。
- 対象PJが変わった：書込みを止めて再照合。別案件へ同じ変更をかけない。
- 価格・NG・基準の不足：不足する判断だけ未確定にし、候補・仮処理・他区間を進める。
- 手順の誤りを直した：[更新方法](../CONTRIBUTING.md)に従って、このGitHubの正本へ毎回保存する。
